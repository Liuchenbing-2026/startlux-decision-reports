共同主线：保留决策语义，复用推理基础设施

03

按职责拆解：改哪里，为什么改

按模型查看“原始行为 → 接入修改 → 保留边界”。模型注册只是入口，不能代替权重加载和数值语义。

StartLux · 4B / 35B-A3B

已交付 rc2

原始行为与缺口

标准因果骨干已有词表头，但普通生成接口不直接返回官方决策协议。

实际修改

加载权重时截取 A–Z 行，末位置特征以 FP32 投影为 26 个分数；官方模板和温度仍在服务层处理。4B 与 35B 分别注册稠密和 MoE 模型类。

这不是唯一可行方案：保留原始框架、在服务层取候选 logprobs 也有历史功能验证；本报告比较的是 rc2 已全量验证的原生 pooling 方案。

startlux_decision.py → StartLuxDecisionPooler · serve_startlux_decision.py

Perplexity Decider · 27B

已交付 rc2

原始行为与缺口

权重包单独存放决策头，要求全注意力双向；只支持 Qwen 骨干不足以正确加载和执行。

实际修改

创建独立权重视图并登记 readout；用 LAST 汇聚接独立线性头；修正模型配置和 Ascend 注意力元数据；复用 autojev 生成问题及答案。

当前 head 使用 BF16，随后转为 FP32 处理候选。不能将这个结果转换描述为 FP32 线性计算，也不能把 eager/graph 一致等同于逐概率对齐 HF。

prepare_pplx_decider.py → PplxDeciderForSequenceClassification → serve_pplx_decider.py

D3 · 27B

已交付 rc2

原始行为与缺口

独立决策头＋双向全注意力，与 Decider 的接入结构相近，但官方输入及精度契约独立。

实际修改

复用 Qwen 骨干，删除无用词表输出头，接 FP32 的 D3DecisionPooler；严格检查 format_id、答案代码、token ID、FP32 和 last pooling。

复用 d3_runtime 的输入准备和输出映射。全注意力双向不代表 GDN 也双向；视频目前明确不接入。

prepare_d3.py → D3ForSequenceClassification → serve_d3.py

D3 Flash · 9B

已交付 rc2

原始行为与缺口

与 D3 27B 采用同类决策格式和读出机制，骨干规模不同。

实际修改

沿用同一 D3 模型类、准备脚本和服务；隐藏维度与槽位数量从 checkpoint 读取，FP32 约束不变，无需复制一套 9B 专属算子。

代码可复用不等于免验收：Flash 仍独立下载校验、运行七项全量对照，并验证图片冒烟与图回放。

prepare_d3.py / D3ForSequenceClassification / serve_d3.py

图示解释输出头的来源；没有将两条路线混装为同一个服务。

04

图模式代码共用，运行策略不同

eager 是逐算子调度；PIECEWISE 图模式把可捕获片段预先记录后回放，减少调度开销。图模式不改变目标决策语义，但填充到不同长度可能改变浮点计算路径，因此必须做概率对照。

eager：先确认模型和协议正确

使用对应 eager 完整补丁，先检查权重、模板、候选顺序、温度及全量精度。D3 / Decider 仍需要 Ascend 双向注意力修复；它不是图模式专属修改。

graph：保持相同输入，独立验证图回放

从干净基线应用 graph 完整补丁，不要叠加 eager 完整补丁。图分支增加同一组通用调度保护；具体是否允许填充由每个模型的配置决定。

必须分开理解：双向注意力修复负责算对；图回放负责减少调度开销；同一套精度验收负责证明优化没有改变本轮输出。不是“每个模型都在两仓各加一套算子”。

06

可直接用于汇报的结论

我们建立了一套可复用的昇腾决策模型接入流程，完成 4 个仓库、5 款模型的 rc2 交付。骨干和调度基础设施共用，候选词表头与独立决策头分别适配，模型特有的注意力、精度和协议保持不变；五款模型均完成 eager 与图模式全量概率对照。

Qwen 骨干、pooling 接口、服务与评测框架输出头来源与精度、模板、温度、候选映射模型注册成功 ≠ 完成适配
D3 与 Flash 同一实现；Decider 共享注意力修复每个权重版本独立验收，包含图执行配置共享代码 ≠ 共享全部实测结论
