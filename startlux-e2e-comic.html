ACT 01

先让业务请求走完一圈

贯穿例子：重复扣款工单。以下对话是流程示意，不是实测预测。

01

业务提出问题

业务系统
这张工单，该转给谁？

应用提交 state、questions、候选与等级定义。比如财务、物流、客服；模型只在给定集合里判断。

动作执行与权限仍由业务系统控制。
02

协议固定语义

官方服务
先把问题写成模型认得的格式。

choice 是选项分布；noul 是“是”的概率；score 是有序等级分布与聚合结果。保留官方候选顺序、模板及问题温度。

每个问题独立渲染；批处理不等于共用一次 state 编码。
03

模型只负责打分

vLLM 引擎
不用先生成一段 JSON。

骨干读取输入，pooling 取最后有效位置；候选头输出 A–Z 的原始 logits。候选截取和归一化在服务层进行。

/classify 的 probs 字段，在此补丁中仍是原始 logits。
04

判断回到业务

业务系统
拿到结构化值，再决定执行。

网关将候选符号映射回业务标签。应用先检查结果与业务规则，低置信度可转人工；阈值需要独立业务验证。

概率不是正确保证；固定可编码规则仍交给规则引擎。

运行时调用链：不要把模型、网关、硬件混成一层

应用

state + questions

官方服务

模板 / processor / 候选协议

vLLM

骨干 / pooling / 候选头

Ascend 后端

metadata / 算子 / 图执行

返回业务

logits → 分布 → 标签

p = softmax(logits[legal_candidates] / temperature)

必须先限定合法候选，再 softmax；先对全部 26 项归一化再截断，会改变概率语义。超过 26 个候选要复用官方分组与汇总逻辑。

第一段适配：让 vLLM 认识模型

模型定义与注册在 vLLM；复用骨干，不在 Ascend 复制模型类。

01

锁定模型包

模型工程师
名字相似，不代表配置相同。

复用 dense / MoE

vLLM 模型层
骨干已有，只补决策读出。

正确加载候选头

权重加载器
先取完整词表中的候选行。

从 lm_head 或 tied embedding 取候选符号对应行，每个张量并行 rank 保留小头。最后有效 hidden 转 FP32 做投影。

校验字母为单 token；缺头直接报错，不能静默随机初始化。

B

候选头：怎样从生成权重得到决策 logits

vllm/model_executor/models/startlux_decision.py

原始 lm_head / embeddingA–Z 行 → FP32 小头LastPool 取 hidden输出原始分数

原行为与问题

不能把整个词表先 softmax，再截 A/B/C；也不能直接取批次张量的最后一行，它可能不对应该请求最后有效 token。BF16 骨干不意味着读出投影也要降精度。

改动后的行为

初始化时校验 A–Z 都是单 token。加载过程中从 lm_head，或共享词嵌入取对应行，在词表分片之前保留小候选头。LastPool 根据 pooling metadata 选最后有效位置，再用 FP32 做线性投影；缺头就抛错。

Ascend 修复：mask 与 causal 必须说同一件事

vllm_ascend/attention/attention_v1.py

common causal按组检查 EncoderOnly局部 causalmask + metadata 同步

原行为与问题

模型设置非因果还不够：混合 GDN / encoder-only 组的 common metadata 仍可能是 causal=True。原实现直接把共享值传给 mask builder 和返回 metadata，可能让 Instant full-attention 仍走因果路径。

改动后的行为

先用当前组的 EncoderOnlyAttentionSpec 求局部 causal，再把同一个结果用于 mask 与 AscendMetadata。关键是“不修改 common_attn_metadata”，避免影响其他组。普通 FullAttentionSpec 继续保持输入标志。

关键代码摘录

    self.kv_cache_spec, EncoderOnlyAttentionSpec
)
attn_mask = self.attn_mask_builder.get_attention_mask(
    causal, self.model_config

正确性边界：这是后端通用语义修复，不需要 Ascend 新增 StartLux 模型类；适用性必须按目标 revision 核对。v1 rc2 路径不需要这段补丁。

用三个分支读懂 metadata 修改

当前组 / 输入原实现修复后理由
FullAttentionSpec / TrueTrueTrue普通因果行为保持
EncoderOnlyAttentionSpec / TrueTrueFalse覆盖错误的共享默认值

服务桥接：保持 token 与概率协议不变

startlux_decide/backends/vllm_pooling.py + official readout.py

官方 prompt精确 token IDs/classify 原始 logits候选与温度后处理

原行为与问题

引擎 /classify 与业务 /v1/systemone 不是同一个协议。若再用聊天模板渲染一遍、自动加特殊 token，或者把 probs 当成已归一化概率，接口虽然返回成功，语义却可能改变。

改动后的行为

官方服务先渲染，再把精确 token IDs 发给引擎，并关闭自动 activation。接收端验证恰好一条结果、26 个有限数值且排除 bool；按 letter_ids 重排返回，校准继续交给官方 readout。

最后一段：验收、业务收益与交付

功能能跑、概率一致、任务正确、图命中、性能收益，是不同的验收对象。

01

协议与输入一致

协议检验员
模板错了，先别怀疑图。

固定模板、token IDs、候选与温度。分别测 choice、noul、score、换序、宽候选、异常输入；核对每问题返回位置。

同一个请求，不同渲染不能直接比较概率。
02

全量精度与逐概率

精度检验员
均分一样，还要看每道题。

七项逐项评分并检查零缺失、零无效。按来源、顺序、ID 与问题配对，比较全部候选概率和选择。DecisionPivot 另按成对准确率算。

固定数据有重复 ID；不能按 ID 去重。
03

公平测加速

性能检验员
把同一批请求交给两种模式。

eager 与 graph 固定权重、设备、输入、并发、预热与计时边界。记录完成请求、决策吞吐、P50/P95、错误率及图命中。

只讲测量方法；性能数值和原始日志不公开。

图片与 AutoThink：沿主线扩展，单独验收

图片链路

图片 → 官方 processor 的尺寸/顺序 → 多模态 /classify → 视觉特征 + 语言骨干 → 相同候选后处理。不要只把图片 URL 拼成文字。

已完成 4B/27B eager 与 graph 的小样本接入；视觉编码器 eager、语言骨干 PIECEWISE。正式视觉基准与 27B 图片官方参考仍缺，不能用文字七项替代。

AutoThink 链路

首次决策 → 置信度判断 → 必要时生成思考 → 再读出/混合概率。它是另一套 checkpoint 与执行路径，不能把 Instant 的单次 pooling 结果当成完整验收。

既有有限样本结果按用户接受口径保留；完整任务覆盖仍需补齐。历史严格概率/一致性失败继续留档，不追认为所有任务通过。
